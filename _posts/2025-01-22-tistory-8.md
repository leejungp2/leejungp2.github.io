<li>MoE 개념(from GPT)주요 특징
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li><b>전문가 모델들</b>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MoE는 여러 하위 모델(전문가)로 구성됩니다. 각 모델은 특정한 문제나 데이터 패턴에 전문화되어 있습니다.</li>
<li>예를 들어, 하나의 전문가 모델은 언어 데이터를 잘 처리하고, 다른 모델은 이미지 데이터를 더 잘 처리할 수 있습니다.</li>
</ul>
</li>
<li><b>게이팅 네트워크(Gating Network)</b>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MoE의 핵심은 <b>게이팅 메커니즘</b>입니다. 게이팅 네트워크는 입력 데이터를 분석하여 어떤 전문가 모델이 해당 입력을 가장 잘 처리할 수 있는지 판단합니다.</li>
<li>게이팅 네트워크는 "어떤 전문가가 활성화되어야 하는지"를 결정하는 역할을 합니다.</li>
</ul>
</li>
<li><b>효율성</b>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MoE는 모든 전문가를 동시에 사용하는 대신, 특정 입력에 맞는 소수의 전문가만 활성화하기 때문에 <b>계산 효율성을 높일 수 있습니다</b>.</li>
<li>이는 대규모 모델을 더 적은 자원으로 효율적으로 실행하는 데 유리합니다.</li>
</ul>
</li>
</ol>
<hr data-ke-style="style1" />예시
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>검색 엔진</b>: 검색어에 따라 특정 전문가가 활성화되어 결과를 제공합니다. 예를 들어, 스포츠 관련 검색어는 스포츠 데이터를 다루는 전문가가 처리합니다.</li>
<li><b>번역 모델</b>: 문장 구조나 언어에 따라 특정 전문가를 활성화하여 더 정확한 번역을 제공합니다.</li>
</ul>
<hr data-ke-style="style1" />MoE의 장점
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>확장성</b>: 대규모 데이터와 모델에도 적용 가능하며, 필요한 전문가만 사용하므로 계산 비용이 절감됩니다.</li>
<li><b>성능 개선</b>: 전문가가 특정 작업에 특화되어 있어 더 정교한 결과를 도출할 수 있습니다.</li>
<li>MoE의 단점</li>
<li><b>복잡성</b>: 게이팅 네트워크 설계와 전문가의 분배가 까다로울 수 있습니다.</li>
<li><b>통신 비용</b>: 여러 전문가가 활성화되면 GPU 간 통신 비용이 늘어날 수 있습니다.</li>
<li>&nbsp;</li>
</ul>
</li>
<li>인공지능, 특히 <b>기계 학습과 딥러닝</b>에서 사용되는 개념으로, 여러 전문가 모델(expert models)을 조합하여 주어진 문제를 해결하는 접근 방식입니다.</li>
</ul>

<h2 data-ke-size="size26"><b>Sparse Mixture of Experts(SMoE)</b></h2>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>개념
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>SMoE: 특정 토큰이 활성화된 일부 전문가만 통과하도록 설계</li>
<li>효율성 극대화, 대규모 모델 비용 문제 해결
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>ex. Google의 <b>Switch Transformer</b></li>
<li><a href="https://arxiv.org/abs/2101.03961">Switch Transformers: Scaling to Trillion Parameter Models with...</a></li>
</ul>
</li>
</ul>
</li>
<li>주요 아키텍쳐
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Mixture of Experts Layer
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>라우터로 입력 전송 &rarr; Gating Layer (which to route를 알려줌) &rarr; 특정 전문가가 process &rarr; individual이 결과를 통합하여 output으로 반환</li>
<li>input = x, router = Wg, Gating wieghts = put the TopK out of soft m ax</li>
</ul>
</li>
<li><b>SMoE의 이점</b>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>성능 향상: 전문가 레이어(MLP)의 용량 확장으로 지식 저장 능력 향상</li>
<li>추론 효율성: 활성화된 파라미터 수가 적어 대규모 추론 시 비용 절감</li>
<li>다양한 언어 및 작업에서 뛰어난 성능: 특히 지식 기반 작업에서 두드러진 성과</li>
</ul>
</li>
<li>도전 과제
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>로드 밸런싱: 추론 시 전문가들 간 작업 부하를 균등하게 분배하는 것이 중요.</li>
<li>해석 가능성: 각 전문가가 어떤 특징을 학습하는지 해석하기 어려움.</li>
<li>압축 및 최적화: 모델 크기를 줄이고 효율성을 극대화하는 연구가 필요.</li>
<li>이상적으로는 전문가 간 부하를 균등하게 분배하여 최적의 성능 달성</li>
</ul>

<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>What does MoEfying MLPs(Multi-layer Perception) give you?
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Moefying = MLP(Multi-Layer Perceptron) 레이어를 Mixture of Experts (MoE) 구조로 변환하는 것을 의미</li>
<li>기존 MLP: Dense 모델에서 MLP는 입력 데이터 전체를 모든 파라미터로 처리하는 방식으로 작동. 모든 토큰이 동일한 계산 경로를 거침.
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MLP는 지식을 저장하고 attention이 알고리즘과 추론을 한다는게 일반적</li>
</ul>
</li>
<li>MoE-fying MLP: MLP 레이어를 여러 전문가로 구성된 구조로 변환하여, 입력 토큰이 게이팅 네트워크를 통해 가장 적합한 몇 개의 전문가에만 전달</li>
<li>효과
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>지식 용량 확장</b>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MLP 레이어를 기존 대비 <b>더 넓게(wider)</b> 확장할 수 있음. 예를 들어, 기존 MLP 대신 8개의 전문가를 추가하면, 각 전문가가 독립적으로 지식을 저장하므로 모델의 지식 저장 용량이 증가.</li>
</ul>
</li>
<li><b>효율성</b>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>모든 파라미터를 활성화하지 않고 필요한 일부 전문가만 활성화하므로 연산 비용이 절감.</li>
<li>활성화된 파라미터 수는 모델 크기와 독립적으로 유지됨.</li>
</ul>
</li>
<li><b>성능 향상</b>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MLP 레이어가 특정 데이터 패턴이나 도메인에 특화될 수 있어 지식 기반 작업에서 성능이 향상됨.</li>
</ul>
</li>
</ul>
</li>
<li>결과
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Mixtral 8x7B 모델은 Mistral보다 좋은 성과를 보임</li>
<li>Vertical access = performance, 가로축 = 파라미터</li>

<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MoE-fying Attention?
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>기존 Attention 구조: Q, K, V는 각각 고정된 Dense 매트릭스(W_q, W_k, W_v)를 사용하여 계산됨. 모든 토큰이 동일한 파라미터로 처리</li>
<li>MoE-fying Attention:Q, K, V 매트리스를 switch layer로 바꾸어 입력 토큰에 따라 가장 적합한 전문가를 선택하고 계산에 활용함</li>
<li>게이팅 네트워크를 통한 라우팅
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>MoE 구조에서 각 입력 토큰은 게이팅 네트워크를 통해 라우팅</li>
<li>ex. Q, K, V 중 각 매트릭스가 활성화된 전문가를 거쳐 계산됨</li>
</ul>
</li>
<li>Sparse 구조
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>기존 Attention 레이어는 모든 매트릭스를 사용하지만, MoE 구조에서는 선택된 일부 전문가만 활성화되어 연산을 수행</li>
<li>이는 계산 효율성을 증가시키고 모델의 확장 가능성을 높임</li>
</ul>
</li>
<li>추가적인 이슈: 안정성
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>FP16(Floating Point 16) 정밀도로 MoE-fying Attention을 훈련할 경우, 수렴 문제(divergence)가 발생할 수 있음</li>
<li>FP32(32-bit Floating Point)를 사용하면 안정성이 개선되지만, 계산 비용이 증가</li>
</ul>
</li>
</ul>
</li>
</ul>
<h2 data-ke-size="size26">Sparse Mixture of Experts(SMoE)</h2>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Myth 1: Mixtral 8x7B에는 전문가 8명이 있다.
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>사실</b>: 각 레이어에 8명의 전문가가 있지만, 이들은 순열적으로 동등(permutationally equivalent)</li>
<li>레이어마다 전문가들의 순서를 바꿔도 동일한 결과를 제공</li>
<li>실제로는 32개의 레이어 &times; 8명의 전문가로, 총 <b>256명의 전문가</b>가 있으며, 레이어 간에는 비교적 독립적</li>
</ul>
</li>
<li>Myth 2: Mixtral 8x7B는 56B(560억)개의 파라미터를 가진다.
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>활성화된 파라미터는 12.9B(129억)개에 불과</li>
</ul>
</li>
<li>Myth 3: 활성화된 파라미터의 수와 비용은 비례한다(cost~active parameters).
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Mixtral 8x7B는 LLaMA 2 13B보다 활성화된 파라미터가 적지만, 전문가 라우팅으로 인해 <b>통신 비용</b> 증가</li>
<li>활성화된 파라미터의 수가 비용에 정확히 비례하지는 않으며, 동일한 파라미터 수의 dense model Mixtral이 약간 더 높은 절대 비용 발생</li>
</ul>
</li>
</ul>

<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>deep NN은 해석하기 어려움</li>
</ul>
</li>
<li>게이팅 신호(Gating Signals)의 해석

<li>Attention 해석 기회: Attention은 특정 토큰에 가중치가 어떻게 할당되는지 시각화 가능

<h2 data-ke-size="size26"><b>Q&amp;A</b></h2>
<p data-ke-size="size16">Q. 왜 SMoE를 사용하는가 Dense 모델 대신 SMoE를 사용하는 이유는? (intensive models that have more knowledges in a confined scope)?</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Dense 모델
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>엣지 디바이스에서는 모든 매개변수를 활성화하지 않아도 되어 잠재력을 발휘</li>
<li>그러나 자원이 제한된 환경에서는 SMoE보다 부담이 적음</li>
</ul>
</li>
<li>SMoE
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>대규모 데이터 센터와 같이 고성능 환경에서는 추론 비용 대비 효율성이 더 뛰어남</li>
<li>특정 입력에 필요한 일부 전문가만 활성화하여 계산 자원을 효율적으로 활용</li>
</ul>
</li>
</ul>
<p data-ke-size="size16">Q. 이미지 및 텍스트를 포함한 multimodal(visual) tasks fine-tuning 문제</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>OpenAI의 ChatGPT, Google의 Gemini 등은 모델 가중치에 접근 권한이 없어 fine-tuning이 제한됨</li>
<li>그 결과 폐쇄형 모델에서는 Google이나 OpenAI에 의존해야 하므로 사용자 제어력이 낮음</li>
<li>Open Source 모델은 가중치에 접근 가능하여 fine-tuning에 유리</li>
</ul>
<p data-ke-size="size16">Q. MoE는 성능 향상을 위해 feedforward 레이어를 어떻게 활용하는가?</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>계산 측면에서 performance가 가장 중요</li>
<li>MoE는 MLP 레이어를 확장(ex. 8배)하여 각 레이어에 더 많은 지식을 저장 가능</li>
<li>게이팅 네트워크를 통해 선택적으로 일부 전문가만 활성화
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>불필요한 파라미터를 비활성화하여 계산 효율성을 증가</li>
</ul>
</li>
<li>Switch Transformer 논문 참고
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>추론 비용 감소와 성능 향상에 중점을 둠</li>
</ul>
</li>
</ul>
<p data-ke-size="size16">Q. 전문가 수가 증가함에 따라 라우팅 및 통신 비용은 어떻게 증가(scale)하는가?</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>요인-전문가의 수, 각 전문가의 규모-에 따라서 병렬처리 방식이 달라짐</li>
<li>하나의 노드에 모두 들어가기 어려울 만큼의 전문가가 있다면
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>노드 간 통신 비용 증가</li>
<li>GPU 간 토큰 라우팅에 따른 비용 발생</li>
</ul>
</li>
<li>전문가 수와 크기가 커질수록 통신 비용이 비례적으로 증가</li>
</ul>
<p data-ke-size="size16">Q. 효율성의 관계는</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Dense 모델
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>엣지 디바이스에서 메모리 제약이 큰 경우 적합</li>
<li>상대적으로 단순한 아키텍처로 안정적인 성능 제공</li>
</ul>
</li>
<li>SMoE
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>대규모 데이터 처리 시 성능 대비 비용 효율성이 뛰어남</li>
<li>사용 사례에 따라 적합한 선택 필요</li>
</ul>
</li>
</ul>
<p data-ke-size="size16">Q. MoE 모델이 특정 작업 전문가(domain-specific expert)보다 더 좋은 성과를 낼 수 있는가?</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>결론: 어려움</li>
<li>특정 작업에 특화된 전문가 모델은 지속적인 fine-tuning을 통해 성능을 최적화</li>
<li>MoE는 일반적인 작업에서 성능이 좋지만 특정 도메인 작업에서 전문가 모델보다 뛰어나지 않을 가능성이 높음</li>
</ul>
<p data-ke-size="size16">Q. MLU가 early layer와 deep layer 모두에 있어야 하나? late fusion tends to work better</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>무작위 순서로 layer를 배치하는 경우에도 꽤 좋은 성과를 냄</li>
<li>이유는 정확히 알 수 없음</li>
<li>성능이 뛰어난 모델을 하고 싶다면 모든 계층에 동일한 아키텍처를 사용하는 게 &lsquo;safe&rsquo;한 방법 / optimizer architecture 찾는 방법도 있긴 함.</li>
</ul>
